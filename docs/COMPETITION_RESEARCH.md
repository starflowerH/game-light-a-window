### 对手总体画像

- **视觉**：普遍使用 AI 生成插画/封面；真正形成统一设计系统的少。
- **交互**：大量“点击下一步”和工具面板；有真实游戏循环的只有 189、192、200、172。
- **AI**：只有 196 明确接入 DeepSeek，但 Key 泄露、无验证流程，反而不符合比赛要求。
- **工程**：绝大多数是单文件；缺少加载态、错误兜底、可访问性、响应式、自动化测试和项目说明。

### 重要安全发现

这也说明：**按比赛要求做“用户自带 Key + 仅内存使用”的流程，本身就是差异化工程亮点。**

## 3. 4 个奖项怎么打

### 最佳视觉设计奖

**赢法：统一的世界观视觉系统，而不是几张漂亮封面。**

必须做到：
- 一个明确的视觉母题（建议：校园夜间情绪气象站 / 会呼吸的纸艺微缩校园）。
- 同一条色彩与字体系统贯穿：开场、主界面、游戏内、结算、说明页。
- 关键动效至少 3 处：入场、反馈、转场；全部服务情绪，不做无意义粒子。
- 封面、截图、演示 GIF 与作品内视觉完全一致。

**不建议**：继续用通用治愈系蓝天草地 + 圆角白卡。现有作品已经饱和。

### 最佳交互体验奖

**赢法：让 AI 成为操作的一部分，而不是聊天框。**

必须做到：
- 3 秒内可开始，30 秒内出现第一次有效反馈。
- 每一个操作都有视觉/声音/触觉式反馈（即使桌面端也用微动效 + WebAudio）。
- 有清晰的状态变化：用户的选择改变场景、音景、角色关系或后续内容。
- 提供跳过、重开、暂停、音量、键盘操作；无死路、无不可逆误操作。

**不建议**：只做“点按钮看下一段文字”。

### 最佳 AI 技术应用奖

**赢法：DeepSeek 驱动核心玩法，且隐私与降级路径完整。**

必须做到：
- 启动时要求输入 DeepSeek API Key，并做一次真实校验；失败给出可理解错误。
- Key 只存内存，不写 localStorage、不发送到自建服务器、不打印日志。
- AI 输出进入结构化 JSON，再驱动游戏状态，而不是直接展示一段文本。
- 有超时、重试、限流、内容安全兜底和本地离线降级。
- 项目说明中写清模型、接口、Prompt 设计、验证方式、隐私处理。

**这是最容易做出断层优势的奖项。** 现有作品几乎没有合格实现。

### 最佳工程奖（完成度奖）

**赢法：像交付产品一样交付，不像交作业。**

必须做到：
- 构建产物可直接部署，无本地绝对路径、无缺失资源。
- 首屏加载 < 3 秒（普通校园网络），总包 < 30MB，建议 < 8MB。
- 桌面 1366×768、1920×1080 正常；移动端不崩。
- 有加载态、空态、错误态、重试、音量/静音、退出确认。
- 有 README、项目说明、隐私说明、素材版权清单、演示视频。
- 最好附一份 1 页评审速览：30 秒看懂亮点。

## 4. 推荐产品方向

### 首选：**《情绪气象站：今天校园是什么天气》**

一句话：  
> 你是校园情绪气象站的值班员。AI 把每位同学匿名投递的一句话，转译成一张“情绪天气图”，你要在有限时间里调度光照、声音、空间与陪伴资源，让校园从局部暴雨恢复成可呼吸的天气。

为什么适合拿奖：
- **视觉**：天然有统一母题——天气、云层、雷达、光、雨、风向；可做出极强辨识度。
- **交互**：拖动云层、调节光圈、布置避雨点、合成声音，不是点按钮。
- **AI**：AI 负责“文本 → 情绪气象参数 JSON → 场景变化”，是核心机制。
- **工程**：状态机清晰，2D Canvas 即可，30MB 内轻松完成。
- **内容**：心理主题正向，但不落俗套；可结合衡阳师范学院校园地标。

核心循环（10–15 分钟）：
1. 收到 3–5 条匿名心事。
2. DeepSeek 返回结构化天气参数（情绪类型、强度、需要的光/声/空间）。
3. 玩家在校园地图上布置光源、避雨亭、树洞、陪伴角色。
4. 播放 20 秒模拟，观察天气变化与同学状态。
5. 结算生成一张“今日校园天气报告”，可重玩不同天气。

### 备选：**《一句话，长成一间房》**

AI 把用户写下的一句话，生成一间可探索的 2.5D 房间的布局、色彩、物件与一段环境音；玩家在房间里移动，收集三个“未被说出口的念头”，最后把房间改造成愿意停留的样子。

优势：视觉上限高、AI 生成物直接可视化、适合最佳视觉/交互。  
风险：美术工作量更大，需要更强的资产管线。

### 备选：**《回声宿舍》**

四人宿舍互动叙事，AI 根据玩家每次说话方式生成室友的“潜台词回声”，但表面仍保持克制。  
优势：叙事强、贴近校园。  
风险：172 号作品已经占据“宿舍互动叙事”心智，正面撞车。

### 明确不要做

- 心理健康综合平台（195/202/204/205 已饱和）
- 通用 AI 树洞聊天（196 已占位且容易同质化）
- 俄罗斯方块/消消乐换皮（与主题结合弱，难拿主题分）
- 纯静态长页 + 呼吸动画（完成度天花板太低）

## 5. 技术栈推荐（按你的情况）

你没有游戏开发经验，但可以自己做内容设计。推荐原则：**少技术、强表现、易部署、易被评审打开**。

### 推荐方案 A：零基础首选

| 层 | 选择 | 理由 |
|---|---|---|
| 构建 | Vite | 一条命令起步，自动打包，产物可直接部署 |
| 语言 | TypeScript（轻量使用） | 比裸 JS 更少低级错误；不需要学复杂类型系统 |
| UI/游戏 | 原生 Canvas 2D + DOM/CSS | 不引入引擎，学习成本最低，完全够做天气/房间/叙事 |
| 动画 | CSS 动画 + 自写 requestAnimationFrame 循环 | 可控、包体小、无需 GSAP |
| 状态 | 一个简单状态机 + localStorage（仅非敏感进度） | 不引框架 |
| 音频 | WebAudio 合成 + 少量免版权音效 | 不依赖大音频文件，包体小 |
| AI | DeepSeek Chat Completions，浏览器直连，用户自带 Key | 符合比赛要求，CORS 已验证可用 |
| 测试 | Vitest（纯逻辑）+ Playwright（1 条冒烟） | 工程奖加分 |
| 部署 | Vite 静态产物 + 任意静态托管 / Pinme | 最简单 |

**为什么不用 Phaser？**  
Phaser 很好，但对你当前目标属于过度工具：场景、物理、资源系统都要学。你的核心是“情绪气象可视化 + 轻交互”，Canvas 2D 更直接。

**为什么不用 React？**  
不是不能，而是 UI 状态很少，引入 React 只会增加构建和调试面。DOM + 原生事件足够。

**为什么不用 Unity/Cocos？**  
导出体积、学习曲线、Web 部署链路都更重；30MB 限制下不占优。

### 推荐方案 B：如果你更想做“游戏感”强的作品

| 层 | 选择 |
|---|---|
| 引擎 | Phaser 4（2D） |
| 构建 | Vite + TypeScript |
| 动画 | Phaser Tweens + 粒子 |
| 音频 | Phaser Sound / WebAudio |
| AI | 同上，DeepSeek 结构化 JSON |

适合：跳跃、探索、节奏、收集类。  
代价：需要 1–2 周熟悉引擎；美术和关卡工作量更大。

### 推荐方案 C：如果你更想做“视觉叙事”强的作品

| 层 | 选择 |
|---|---|
| 渲染 | PixiJS 8（2D WebGL） |
| 构建 | Vite + TypeScript |
| UI | DOM 覆盖层 |
| 动画 | Pixi 滤镜/位移 + CSS |
| AI | 同上 |

适合：房间、天气、粒子、光影。  
代价：比 Canvas 2D 多一层渲染概念，但视觉上限更高。

### 我的明确建议

**用方案 A。**  
理由：
- 你的优势在内容和设计，不在引擎经验；
- 情绪气象站的核心是状态变化和氛围，不需要物理引擎；
- 30MB 限制下，Canvas 2D + WebAudio 最稳；
- 工程奖看的是完整度和交付质量，不是技术栈复杂度。

## 6. 推荐架构（方案 A）

```text
src/
  main.ts                 入口：加载、路由、错误兜底
  ai/
    deepseek.ts           Key 校验、请求、超时、重试、JSON 解析
    prompts.ts            系统提示词与输出 schema
    fallback.ts           离线/失败时的本地规则
  game/
    state.ts              全局状态机（title/onboarding/play/result）
    weather.ts            天气参数 → 视觉/音频映射
    loop.ts               requestAnimationFrame 主循环
  scene/
    station.ts            校园气象站 Canvas 场景
    particles.ts          雨/雾/光粒子
  ui/
    keyGate.ts            启动页：输入并校验 DeepSeek Key
    hud.ts                状态、提示、音量、重开
    report.ts             结算报告
  audio/
    ambience.ts           WebAudio 环境音合成
  data/
    letters.ts            示例匿名心事（离线可用）
  styles/
    tokens.css            色彩/字体/间距设计令牌
    main.css
tests/
  ai-schema.test.ts
  state.test.ts
e2e/
  smoke.spec.ts
```

### AI 输出 schema（关键）

不要让模型返回散文。要求返回严格 JSON：

```json
{
  "weather": "light_rain",
  "intensity": 0.62,
  "palette": ["#6C8EBF", "#F2C6A0", "#2E3A59"],
  "needs": ["quiet", "light", "companionship"],
  "message": "今天不需要立刻放晴。",
  "sceneActions": [
    { "type": "spawn_rain", "amount": 0.6 },
    { "type": "add_light", "position": "east_gate", "warmth": 0.7 }
  ]
}
```

前端必须：
- 用 JSON Schema 或手写校验；
- 非法输出直接走 fallback；
- 不把用户原始心事写入 localStorage；
- 不在控制台打印 Key 或完整请求头。

### Key 安全流程

1. 启动页要求输入 `sk-...`。
2. 用一次最小请求验证（`max_tokens: 1`）。
3. Key 只保存在内存变量中。
4. 页面刷新即清除；提供“清除 Key”按钮。
5. 请求直连 `https://api.deepseek.com/chat/completions`。
6. 项目说明写明：不收集、不上传、不存储、不他用。

> 已验证 DeepSeek API 对浏览器跨域请求返回 CORS 允许，可直接从静态页面调用。

## 7. 冲奖执行顺序（建议 3 周）

### 第 1 周：可玩骨架
- Day 1–2：确定视觉母题、色彩、字体、3 个核心画面。
- Day 3–4：搭 Vite + Canvas 场景 + 状态机。
- Day 5–6：接入 DeepSeek，完成 Key 校验 + JSON schema + fallback。
- Day 7：做出 1 条完整 5 分钟体验。

### 第 2 周：内容与打磨
- 加入 6–8 条匿名心事、3 种天气、3 套场景反馈。
- 完成音频、动效、转场、结算报告。
- 做桌面/移动适配与键盘操作。
- 补空态、错误态、加载态。

### 第 3 周：交付与展示
- 写 README、项目说明、隐私说明、素材清单。
- 录制 60–90 秒演示视频。
- 做 1 页评审速览。
- 用 Playwright 跑冒烟测试。
- 压测普通网络首屏；总包控制在 8MB 内。
- 提交前用无痕窗口 + 未登录状态完整走一遍。

## 8. 评审现场 30 秒话术模板

> 这是一个“校园情绪气象站”。每位同学匿名投递一句话，DeepSeek 把它转成结构化的情绪天气参数，驱动校园场景里的雨、雾、光和声音。玩家不是读一段 AI 文案，而是通过布置光源、避雨点和陪伴角色，改变这片天气。  
> 所有 API Key 只存在内存，不上传、不存储；AI 失败时自动切换到本地规则，体验不中断。  
> 我们希望让“被看见”不是一句口号，而是一次可以被操作、被反馈、被记住的天气变化。

## 9. 风险清单

| 风险 | 应对 |
|---|---|
| 上传权限未开通 | 尽早联系主办方/QQ 群确认 |
| DeepSeek Key 校验失败 | 提供清晰错误、示例说明、重试 |
| 评委现场网络不稳 | 本地 fallback + 演示视频 |
| AI 输出不稳定 | JSON schema + 校验 + 重试 + 默认值 |
